## Description

Three merchants have reported that the dashboard's daily volume does not match their settlement statement.

Two of them are off by a few cents on high-volume days. The third, a merchant in Berlin, sees an entire day of volume attributed to the wrong date.

Support has not been able to reproduce it reliably, and the pattern is not obvious from the tickets. We do not know yet whether these are one bug or several.

## What we know

- The Berlin merchant is the only reporter outside North America.
- The discrepancy grows with transaction count, which suggests accumulation rather than a single bad record.
- One merchant with heavy refund activity reports totals that look **too high**, not too low.
- Nobody has checked whether the payouts screen agrees with the payments screen.

## What we need first

A written diagnosis before anyone edits code: which files are involved, what the root cause is for each symptom, and which of the three reports share a cause.

Do not fix it in the same session that finds it. Read first.

## Diagnosis

Found during the NWP-101 pre-ship pass; confirmed by reading the code and by tests on the NWP-201 branch. The three reports are three causes, plus a fourth the reporters could not have seen.

| Symptom | File | Root cause | Status |
| --- | --- | --- | --- |
| Berlin merchant sees a day of volume on the wrong date | `src/data/metrics.ts:25` | `dailyVolume` keyed each payment by `toLocaleDateString("en-CA")` — the server's local date — while its buckets came from `lastUtcDays` in UTC. On a server ahead of UTC, a payment late in the UTC day lands on the next day; on the newest day of the window it has no bucket and `if (!bucket) continue` drops it silently. | Fixed in PR #159 with `utcDayKey`; test fails on the old code under `TZ=Europe/Berlin` |
| Off by a few cents on high-volume days | `src/data/metrics.ts:31-43` | Accumulated `amount / 100` as floats and rounded back at the end. Violates ORG-STANDARDS #1–2; at this seed volume the rounding hides the drift, at real volume it would not. | Fixed in PR #159: sums minor units, returns them as-is |
| Amounts sort out of order on the payments table | `src/data/queries.ts:80` | `sortPayments` compared amounts as strings, so 999 sorted after 1000. Not in the original reports; found on the same pass. | Fixed in PR #159 with a numeric compare; test fails on the old code |
| Heavy-refund merchant sees totals that look too high | `src/data/metrics.ts:53-55` | Headline "Gross volume" is captured + refunded. Whether gross should include amounts later refunded is a definition question for Finance, not a code defect. | Open — needs a product answer before anyone edits it |

Not a cause: the payouts screen sums minor units correctly (`generate.ts` and `analytics.ts` reduce integer amounts); the only `/ 100` left is at the chart boundary (`analytics.ts:54,73`, `overview/page.tsx:16-17`), which is display-only.
