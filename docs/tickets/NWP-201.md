## Description

Ops issues virtual cards by messaging the platform team, who create them by hand. It takes hours, it happens twelve to twenty times a week, and last month two cards were created with the wrong spend limit because the request was in a Slack thread.

Merchants use these for vendor subscriptions, ad spend, and contractor tools. They are single-merchant, always virtual, and they need a limit from the moment they exist.

Put it in the console. Ops should be able to issue a card, see the cards they have issued, and open one to check it.

## Scope

This is the Build Battle ticket. You have **45 minutes**. Hit the core criteria first — they are what most of the score is. Stretch goals are there to separate the field, not to be finished by everyone.

### Core — do these first

- [ ] **Issue a card.** A form or dialog takes a nickname, the merchant, a spend limit, and a currency. Submitting creates the card and it appears in the list.
- [ ] **Card list.** A `/cards` route showing every issued card: nickname, merchant, masked number, spend limit, status, and created date.
- [ ] **Card detail.** Opening a card shows its full record and its spend against the limit.
- [ ] **Generated card numbers.** Numbers are generated server-side on the `4242` test BIN and carry a valid Luhn check digit.
- [ ] **Reveal once, mask forever.** The full number is shown exactly once, on the success screen right after creation. Everywhere else it is `•••• 4242`.
- [ ] **Server-side validation.** Reject a missing merchant, a zero or negative limit, a limit above 5,000,000 minor units, and any currency outside `USD`, `EUR`, `GBP`. The client is not trusted.

### Stretch — where the leaderboard gets decided

- [ ] **Freeze and unfreeze** a card from the list without a full page reload.
- [ ] **Spend progress** on the card detail: a bar showing spend against the limit, turning amber past 80%.
- [ ] **Merchant category lock**, chosen at issue time and shown on the card.
- [ ] **Tests.** Unit tests on the Luhn generator and the status transitions, added beside the code they cover, with `npm test` passing.
- [ ] **Empty and error states** that are written, not default.

Those five are what the board asked for. ## The rules that make this real

Get these wrong and the card looks fine but the code is not shippable:

1. **Money is integer minor units.** A `$250.00` limit is `25000`. Never a float, never a string with a dollar sign. Format once, at the edge.
2. **Never persist or display a full card number after creation.** Store the last four and the generated number's reference. The reveal is a one-time response, not a field you can re-read.
3. **Status is a state machine.** `active → frozen → active`, and either can go to `cancelled`. `cancelled` is terminal — nothing comes back from it.
4. **The `4242` BIN is not optional.** Every generated number starts with it, so nothing in this repository can ever resemble a real card.

## Out of scope — do not build these

- **Persistence.** The console runs against an in-memory store seeded from JSON. Cards you create live until the dev server restarts. Real persistence is NWP-203. Do not add a database, an ORM, or a migration; it will not earn points and it will cost you the clock.
- Authentication, roles, and permissions.
- Real card network calls. There is no issuer here and there is not going to be one today.
- Editing a card's limit after issue. That is NWP-202.
